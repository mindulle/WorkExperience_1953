# 구글맵/캐치테이블 리뷰 수집의 파이프라인 편입 가능성 검토

2026-07-29 기준. 상은/주은/선영님이 Claude in Chrome(AI 브라우저 세션)으로 구글맵·캐치테이블 리뷰를 일회성 수집한 것을, `src/pipeline/`처럼 지속적으로 재실행 가능한 파이프라인에 편입할 수 있는지 검토한 기록입니다.

## 왜 지금 방식은 그대로 파이프라인에 넣기 어려운가

기존 수집기(`naver_review_collector.py`, `youtube_collector.py`)는 **공식 API + 결정론적 코드**입니다. 입력이 같으면 출력도 같고, 사람 개입 없이 크론/CI로 무인 실행이 가능합니다.

반면 구글맵/캐치테이블 수집은 **AI 에이전트가 그때그때 화면을 보고 판단하며 브라우저를 조작**하는 방식이었습니다. 이미 실패 사례가 있었습니다 — 주은님의 수집 리포트(`1953_review_collection_summary.txt`)에 "리뷰 탭이 활성화되지 않고 리뷰 패널 스크롤이 타임아웃되어 추가 확보에 실패함"이라고 명시되어 있습니다. 이런 방식은 코드 한 줄 안 바꿔도 페이지 구조가 바뀌면 실패하고, 실행할 때마다 AI 세션 비용이 들며, 실행 시간도 깁니다.

## 옵션 비교

### A. 지금 방식 유지 (AI 브라우저 세션, 비정기 재실행)
- 장점: 이미 검증됨, 추가 개발 불필요
- 단점: "지속 파이프라인"이라 부르기 어려움 — 매번 사람이 트리거해야 하고, 매 실행마다 AI 세션 비용 발생

### B. 자체 결정론적 스크래퍼 (Playwright/Selenium) 직접 개발
- 장점: 다른 수집기와 동일한 패턴으로 `src/pipeline/collect/`에 편입 가능, 실행 비용 낮음
- 단점: 구글맵 리뷰 DOM은 지연 로딩(lazy-load) + 스크롤/펼치기 기반 JS 렌더링이라 셀렉터가 자주 깨짐 → 유지보수 부담을 우리가 직접 짐. 개발 공수도 상당함

### C. 유료 스크래핑 API/서비스 이용 (비용 지불 가정)
구글맵 리뷰 전용 상용 서비스들이 이미 존재하며, 이 프로젝트 규모(6개 지점, 월 1회 정도 갱신)엔 비용이 미미합니다.

| 서비스 | 가격 (2026년 기준) |
|---|---|
| Apify (Google Maps Reviews Scraper) | $0.25 / 1,000건, $29/월 플랜은 월 58,000건 포함 |
| Outscraper | 무료 500건 이후 약 $3 / 1,000건 |
| SerpApi (Google Maps SERP API) | $1.00~1.50 / 1,000건 |

→ 6개 지점을 월 1회 갱신하는 정도면 사실상 무료~월 몇 달러 수준. 유지보수(셀렉터 깨짐 대응)를 벤더가 대신 떠안는다는 게 B안 대비 가장 큰 장점입니다.

**다만 "합법/안전"과는 별개 문제입니다.** 2025년 12월 Google이 SerpApi를 상대로 DMCA 위반(구글의 보안 조치 우회, robots.txt·ToS 위반) 소송을 제기했고, Google 측은 "검색 결과 콘텐츠에 대한 자동 접근은 ToS와 robots.txt로 명시적으로 금지된다"는 입장을 명확히 밝혔습니다. 이 특정 소송은 2026년 7월 21일 법원이 SerpApi의 기각 신청을 받아들이며 종결됐지만, 이는 "스크래핑이 합법이라고 법원이 확정 판단했다"는 뜻이 아니라 이번 소송 건이 절차적으로 기각됐다는 의미에 가깝습니다. 즉:
- Google의 ToS는 여전히 자동 수집을 명시적으로 금지하고 있고, Google은 실제로 이를 소송으로 집행하려는 의지를 보였습니다.
- 스크래핑 벤더(Apify/Outscraper/SerpApi 등)를 쓰더라도, ToS 위반의 법적 책임 소재는 최종적으로 콘텐츠를 상업적으로 활용하는 쪽에도 걸릴 수 있어 완전히 자유롭지 않습니다.
- 다만 이 프로젝트는 비상업 학습 목적(일경험 프로그램)이고 규모도 작아, 실제 집행 리스크는 낮다고 볼 수 있습니다 — RULES.md §2.1을 이미 멘토 협의 하에 완화한 맥락과도 일치합니다.

### D. 구글 공식 Places API (Place Details의 reviews 필드) 병행
- 장점: 100% 합법, 스케줄링 용이, 무료 크레딧 존재
- 단점: 지점당 "관련성 높은" 리뷰 **최대 5개**만 제공 — 지금 수집한 양(지점당 수십~수백 건)에 크게 못 미침. 보조 수단으로는 유효하나 대체는 불가능
- **(2026-08-20 추가) 5개 제한은 결제 등급으로 풀 수 없음:** Places API는 구조적으로 5개까지만 반환하도록 설계돼 있어 사용량/결제 등급을 올려도 그대로입니다. 전체 리뷰를 받으려면 별도 API인 **Google Business Profile API**(`accounts.locations.reviews.list`)를 써야 하며, 이건 결제 등급이 아니라 **권한(OAuth) 문제**입니다 — 사장님(또는 회사) 명의 계정이 각 지점 Business Profile의 Owner/Manager로 등록돼 있어야 하고, 그 계정으로 OAuth 인증을 받아야만 호출할 수 있습니다. **지금 단계(일경험 프로젝트, 샘플 시연)는 Places API 5개로 충분하다고 판단해 이 경로를 채택했고**, 실제 기업 핸드오프 시점에 사장님이 Business Profile 소유권 확인 및 OAuth 승인을 마치면 바로 전환할 수 있도록 코드에 스위치 지점을 미리 마련해 두었습니다 (`src/pipeline/collect/google_map_collector.py`의 `GOOGLE_MAPS_REVIEW_PROVIDER` 환경변수 및 `get_reviews_via_business_profile()` 함수 — 현재는 미구현 스텁).

### E. Appium 기반 모바일 앱 자동화 (캐치테이블/배달의민족 등)

캐치테이블·배달의민족은 앱 안에 리뷰 데이터가 더 풍부하게(구조화된 태그, 사진 등) 들어있을 가능성이 있습니다 — 다만 실제로 그런지는 **아직 확인 전**입니다. 검토 결과(2026-07-29, RULES.md §2.1에 반영 완료) 이 접근은 세 갈래로 나뉩니다.

1. **앱 UI를 그대로 조작(로그인 없이 화면 읽기)** — 지금 웹에서 하던 것과 같은 성격의 자동화. 허용.
2. **비공개(문서화되지 않은) API를 관찰해 재사용** — 인증서 고정 등 기술적 보호조치를 무력화하지 않고, 일반 TLS 트래픽을 프록시로 관찰해 앱이 자체 호출하는 엔드포인트를 찾아 그대로 재사용하는 정도. **조건부 허용** (앱이 인증서 고정을 안 쓸 때만).
3. **기술적 보호조치 자체를 무력화**(인증서 고정 우회, 암호화 해독 등) — **여전히 금지**. 웹 검색 결과 모바일 앱 스크래핑은 "웹 스크래핑보다 보호된 인프라에 더 가깝다"는 평가가 일반적이라, 이 범주에 해당하는지부터 확인이 중요합니다.

즉 Appium 자체는 도구일 뿐이고, 관건은 "①②번으로 충분한가, ③번(보호조치 무력화)까지 가야 하는가"입니다. 이건 실제로 앱을 열어서 **로그인 없이 리뷰 목록이 보이는지, 그리고 인증서 고정을 쓰는지** 확인하기 전에는 판단할 수 없습니다.

**제안하는 다음 단계 (개발 착수 전 확인 필요):**
1. 캐치테이블·배달의민족 앱을 로그인 없이 열었을 때 리뷰가 보이는지, 인증서 고정을 쓰는지 확인
2. 보인다면 → 실제로 웹 대비 더 풍부한 정보(사진, 구조화 태그 등)가 있는지 확인해 투자 가치 판단
3. 로그인이 필요하거나 인증서 고정 등 보호가 있다면 → ②번 범주이므로 지금 단계에서는 보류하는 걸 권장

또한 모바일 앱 스크래핑은 웹 스크래핑([C안](#c-유료-스크래핑-api서비스-이용-비용-지불-가정))과 달리 Apify/Outscraper 같은 성숙한 상용 서비스 생태계가 훨씬 얇습니다. 벤더에 맡기기보다 직접 구축·유지해야 할 가능성이 높습니다.

## 캐치테이블(및 배달의민족)은 사정이 다릅니다

구글맵과 달리 캐치테이블은 **웹 기준으로 전용 스크래핑 상용 서비스가 존재하지 않습니다** (검색 결과, Apify/Outscraper류 마켓플레이스에 캐치테이블 전용 상품이 없음). 캐치테이블 자체도 리뷰 데이터 제공을 목적으로 설계된 서비스가 아니라 예약 플랫폼입니다. 이 채널을 웹에서 지속 자동화하려면 100% 커스텀 개발이 필요하고, 참고할 만한 기존 도구/사례가 없어 유지보수 부담이 B안보다도 큽니다. 앱 경로(E안)는 위 확인 단계를 거친 뒤 판단합니다.

## 결론 (현재 판단)

- **구글맵**: 유료 스크래핑 API(C안, 특히 Apify — 비용이 가장 저렴하고 이 프로젝트 규모에 적합) + 공식 Places API(D안, 소량 보조용) 조합이 "지속 편입"의 현실적인 답에 가깝습니다. 법적 리스크는 0은 아니지만, RULES.md에서 이미 감수하기로 한 리스크 수준과 결이 같습니다.
- **캐치테이블/배달의민족**: 웹 경로는 지속 자동화의 명분이 약합니다. 앱 경로(E안)는 "로그인 없이 리뷰가 보이는지" 먼저 확인한 뒤 착수 여부를 결정하는 게 순서에 맞습니다. 그 전까지는 지금처럼 비정기 수동/반자동 수집(A안)을 유지하는 게 안전합니다.
- **비용이 드는 결정(유료 스크래핑 API 가입 등)은 멘토 리뷰 대상이므로, 실제 가입/결제 전에 옵션·비용·리스크를 정리해 먼저 확인받습니다.**
